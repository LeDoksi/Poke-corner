# T08 commit/exit barrier diagnosis (pinned 875afa25d56e3431ac1c585e572d6300610f989b)

Observed: one full-suite run failed MigrationTests.ConsecutiveCommitsUsePublishedSnapshotAndExitWaitsForBoth at migrationTests.cs:500 (disk ShopCoins 19, expected 22). Isolated 1/1 and later full 627 passed. No trace of the failing run survives here, so its exact schedule is unproven.

The test calls one, two, and exit in that order while the first write is held (migrationTests.cs:491-499). AppState.CommitAsync makes two await the first idle task (AppState.cs:61-65); FlushAsync also waits only while IsCommitting is true and then obtains a snapshot and submits it to the writer in separate steps (AppState.cs:85-88). The first commit writes/publishes 19, clears IsCommitting, and completes idle (AppState.cs:68-82). Because continuations are asynchronous, the test's queued two and exit can resume on separate thread-pool threads. A feasible interleaving is: exit sees IsCommitting=false and captures 19; two enters CommitAsync and captures/commits 22, receiving writer sequence N; exit submits its already captured 19 and receives sequence N+1. Both tasks complete, live coins are 22, disk coins are 19. The writer intentionally orders writes by submission sequence, not semantic snapshot age (BackgroundSaveWriter.cs:67-87, 123-155). Thus Task.WhenAll before the assertion does not prevent this result.

This is a real possible stale-snapshot race under concurrent callers, but the writer explicitly requires Post/Flush/CommitAsync calls from one UI thread (BackgroundSaveWriter.cs:3-5). The test does not use the existing WpfTestHost dispatcher, unlike adjacent UiContinuationRemainsFreeWhileCommitAndExitWait (migrationTests.cs:464-485). On a single dispatcher, the two continuations cannot interleave inside FlushAsync's synchronous snapshot-and-submit interval: if exit runs first its 19 sequence precedes two's 22, and if two runs first exit waits for it. The intermittent failure therefore cannot alone establish a supported-runtime defect. The exact failing interleaving remains unobserved.

Smallest deterministic gate for the existing contract: run creation of one, two, and exit on WpfTestHost.Run; hold first writer callback; assert two and exit are incomplete before its release; release the write, await all tasks, then assert live and disk 22. A separate gate for waiting on an active second commit should signal from the second update, create exit only after that signal, hold the second writer callback, and assert exit remains incomplete until it is released. The current test does not guarantee exit waits for both queued commits: on one dispatcher exit may resume and commit 19 before two enters, after which two commits 22 and determines the final disk state. Use explicit TaskCompletionSource gates, not sleeps or arbitrary Task.Run scheduling. This belongs in migrationTests.cs. If concurrent AppState entry points are a product requirement, add a separate forced-interleaving test for snapshot-before-enqueue and fix AppState.FlushAsync's coordination with queued commits/snapshot submission; changing BackgroundSaveWriter ordering would mask the older snapshot without identifying it.

## T02 shutdown follow-up

The UI-thread contract does not remove the exit gap. After the first commit publishes 19 and signals its per-commit idle TCS (AppState.cs:74-82), both the already requested second CommitAsync and FlushAsync are eligible to resume. If FlushAsync resumes first, it sees IsCommitting=false, snapshots 19, submits a flush commit and can complete before the queued second starts. ShutdownApp then calls Shutdown immediately after the await (App.xaml.cs:883-923). OnExit skips another save because _isExiting is true and stops the writer (App.xaml.cs:1009-1035); a second commit that has not run or has only queued its write may be abandoned/canceled. Even if a test later awaits Task.WhenAll and sees final disk 22, that does not prove the application can safely shut down at the earlier FlushAsync completion.

This violates the T02 contract stated in GLOBAL-UPDATE.md:253: while a commit is pending, exit must not write older live state over the new result. The minimal boundary is in AppState: register each requested CommitAsync synchronously before its first await, and make WhenIdle / FlushAsync await completion of all commits already requested when the exit barrier is taken. A count plus shared drain TCS, or an equivalent registered commit tail, is enough on the existing UI dispatcher; no arbitrary-thread API expansion is required. ShutdownApp can then rely on its current await and reach Shutdown only after the registered queue drains and the final snapshot is written. This needs a gated UI RED test that forces exit to resume before the second queued commit and checks that exit remains pending until the second publishes.
