# Глобальный апдейт PokéCorner — подробный план перехода

> **Для следующих чатов:** выполнять одну готовую задачу за раз. Применять `superpowers:executing-plans`; при явно выбранной работе с агентами — `superpowers:subagent-driven-development`. Чекбоксы отмечать только после проверенной поставки.

**Цель:** внедрить подготовленный глобальный апдейт в WPF, сохранив коллекцию и реализовав единые игровые правила без повторных выдач.

**Архитектура:** существующие Core/App и общий JSON store. V2 сохраняется отдельно в state-v2.json; общие правила XP, вариантов ресурсов, инвентаря и подтверждённой записи используются всеми механиками. Runtime получает только каноническую ресурсную поставку; архив подготовки остаётся историей.

**Стек:** .NET 8, WPF/XAML, xUnit, WiX; существующие GIF/аудио/фоновые сохранения. Новая БД и зависимости не требуются.

**Спецификации:** `GLOBAL-UPDATE.md`, `docs/design-v2/final/FINALIZATION.md`, `BALANCE.md`, `MIGRATION.md`, `SCREENS.md`, `IMPLEMENTATION.md` и тематический файл механики. Числа берутся из генерируемых JSON, картинки задают композицию.

## Общие ограничения

- GUID, реальные достигнутые виды, shiny, уход, даты, характеры, клички, избранное, валюта и настройки сохраняются. Только невылупленные покупные PendingEggs удаляются по принятому решению.
- В отсутствие файлов — новая игра. Ошибка загрузки не разрешает стартовый пакет или autosave. V1 и backup не перезаписываются при миграции; существующий повреждённый v2 не импортирует v1 повторно.
- Новая шкала: уровень1/XP0; 40 уровней, пороги10/20/30/40=1200/2800/4800/6400. Уход отделён от XP.
- Один поход и одно гнездо. Участники освобождаются при claim/hatch. Ready не откатывается при переводе часов назад. Исходы сохраняются в согласованный момент.
- Гарантированная часовая ставка основных ягод не ниже2; поэтому30мин≥1 и одинаковые стартовые условия дают одинаковую отдачу в час. Coins/events сохраняют штрафы. Следопыт — относительный множитель итогового p, cap95%.
- Новые выдачи используют CanObtain(species,variant); девять неподдержанных shiny не выдаются. Существующие shiny не удаляются/не превращаются в обычных.
- Любое ресурсное действие сначала собирает новый снимок, затем ожидает CommitAsync; только успех публикуется в UI. Ошибка оставляет предыдущий снимок и допускает повтор. Autosave не подтверждает операцию.
- Комната фиксированная, полка3; сон, модульная мебель, формы и одежда не входят в поставку. Общие реакции, независимая громкость эффектов, Windows reduced-motion.
- Все команды shell предваряются rtk. Реальное сохранение используется только как резервная копия после прохождения синтетических фикстур. Настройки Windows/установка MSI требуют обычных системных разрешений.

## Пять обязательных классов проверки

1. Повреждённый/семантически неверный/будущий save: исходный файл не меняется, новая игра не запускается (T02).
2. Двойное действие или отказ I/O в commit: ресурсы, исход и ID не раздваиваются (T05/06/08/11/13/15/16).
3. Legacy ветвь с cosmetic override и отсутствующий checkpoint: форма сохранена, немедленный необратимый уход исключён (T02).
4. Unsupported shiny и частично доступное семейство: нет подмены признака или перескока звена (T01/07/10/13).
5. Закрытые виды, несколько экземпляров, компактное окно и150/200%DPI: нет утечки скрытых свойств или перепутанного действия (T04/09/12/14/17/18).

## Контракты данных

В T02 добавить в существующую модель SchemaVersion2, CatalogRevision, BalanceRevision, MigrationId, CurrentSpeciesId, FamilyRootId и LegacyOrigin. `TotalXp` и TraitIds принадлежат экземпляру; level/tier вычисляются. Инвентарь использует канонические строковые ID и неотрицательные количества. Рациональный остаток сериализуется numerator/denominator; журнал выдачи хранит ID, фазу и сохранённый результат. Родительские GUID и источник нового экземпляра сохраняются для достижений. Точные поля, состояния и восстановление описаны в MIGRATION.

CommitAsync уже реализован и проверен в текущем коде. T02 владеет его включением в единый барьер мутаций/автосохранений и публикации: пока операция ждёт commit, старый live-state не передаётся Post/Flush. Остальные действия откладываются либо явно отклоняются как занято; activity deltas сохраняются и применяются после публикации. Выход ждёт завершения операции, без синхронного ожидания UI continuation. Ошибка возвращает прежнее состояние. Проверить поздний Post старого снимка во время await, выход и накопление активности.

Единственное подтверждение записи — `Task BackgroundSaveWriter.CommitAsync(SaveData data)`. Метод фиксирует снимок при вызове, завершает Task после записи, не скрывает отказ I/O. Потребители не подменяют предыдущий live-state до успеха и не восстанавливают целиком стартовые объекты при получении.

Новые имена сервисов ниже фиксируют владение и операции; конкретные параметры формируются из данных MIGRATION/JSON в первом тесте задачи. Не добавлять независимые копии общих правил. Для UI один persisted result отображается после commit; анимация не является частью транзакции.
