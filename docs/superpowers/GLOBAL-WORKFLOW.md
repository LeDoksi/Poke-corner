# Последовательная работа над глобальным обновлением

Прямое решение пользователя: промежуточное ревью проверяет необходимое текущему этапу. Визуальную калибровку выполняем после сборки всего обновления. Это правило относится к данному проекту; глобальные настройки агентов не меняются.

## Incorrect

Перекрашивать старый экран, запускать отдельного агента ради шрифта, затем проверять тени и переставлять элементы в представлении, которое скоро заменится. Называть такую проверку приёмкой нового UI.

## Correct

1. Сначала готовые зависимости, схема, механики и необходимые рабочие пути UI. Экраны строятся сразу по утверждённым макетам и общим токенам.
2. На этапе — функциональные тесты и ревью логики, данных, сохранений, границ состояния, отмены/повтора. Критичный UX-блокер, безопасность сброса или потеря данных исправляются сразу. Временный вид не полируется.
3. Затем все новые экраны, реальные состояния и общие реакции собираются в приложении.
4. В T20 — единая матрица визуальной приёмки: размеры/DPI, все экраны/состояния, типографика, цвета, размещение. Материальные правки применяются согласованными пакетами, затем проверяется исправленный пакет.

Субагент получает содержательную задачу с ясным владением или существенный пакет review-правок. Одиночный цвет/шрифт/отступ не повод для отдельного запуска. Сохранения/конкуренция требуют тщательного ревью независимо от визуальной стадии. Дизайн-система фиксируется по окончательно собранному интерфейсу; промежуточный каркас не выдаётся за законченную поверхность.

Перед исправлением старой механики сверять её сохранение в канонической спецификации. Уже исключённую механику удалять из runtime; не развивать её на основании старого кода или неточного промежуточного отчёта. Уже заработанный прогресс и явно утверждённые исключения миграции проверять отдельно.
